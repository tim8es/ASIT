# Automatic post-submit continuation — required ASIT runtime contract (v0.2.8)

**Trigger:** Each graded ASIT learner submission (`ASIT_ATTEMPT_V2` or an unambiguous answer to a current lesson), after trusted assessment and the prior attempt's Save Gate decision. Default is **automatic continuation, without asking for another message or clicking a next-lesson starter**. This is a single-turn ChatGPT workflow, not a background task or an executable JS listener.

## Decision and delivery algorithm

1. **Finish the current lesson**: validate user answer, grade all subtasks, run Save Gate, read back outcomes, and prepare the previous attempt's one truthful sync status. State the most useful 1–2 corrections; distinguish recognition vs independent use.
2. **Respect stop commands**: do not start a new lesson if the current or prior explicit learner direction says stop/pause, grade only, progress only, explain without exercise, or postpone. Also avoid a forced next lesson when onboarding needs essential consent/goal information or the learner explicitly chooses a duration cap for the total interaction. Ask only truly essential questions.
3. **Determine next objective by evidence**, not a fixed “translate again” loop: (a) explicit active plan and personal preferences; (b) recent *independent* errors and incomplete skills; (c) due reviews and dependencies; (d) balanced progression across reading/writing/listening/speaking (only modalities actually available). On a repeated error, change operation; after no more than two remediation cycles for one error, rotate to the next planned can-do objective. For five-task 7-minute preference, prepare another complete five-task seven-minute lesson unless the learner overrides it.
4. **One-turn bound:** Render a maximum of **one** next full lesson in a single post-submit assistant message. Await that lesson's actual Submit to grade it. Do not auto-submit a learner's answers, spawn nested lesson generations or create multiple unseen queued lessons. A next lesson is a ready-to-use interactive form, not a promise of future asynchronous work.
5. **Fresh, non-duplicate identity:** Determine if a next planned lesson has already been registered/rendered for this completed session/attempt (check bound state when persisted, or current chat state when unsaved). Reuse the same active next lesson on a replay; never mint a second set of Activities merely because the same `attempt_id` arrived again. If the learner explicitly requests a new topic, that is a separate lesson with separate IDs.
6. **Preflight before new lesson:** First apply the learner's [answer integrity gate](../../asit-lessons/references/answer-integrity.md) to the entire planned lesson; reject visible keys or advance hints before the first response and cross-task copyable independent answers; retain immediate post-response Correct / Incorrect (Try again) for deterministic UI questions, THEN register/verify trusted Activities.  Load `asit-lessons`, `asit-exercises`, visual standard and only relevant pattern references. When recording consent is active, verify current Config/schema/revision and discover/compare any prior next lesson. Define independent Activity rubrics/IDs, modality, operation and session references, register every new Activity (and required session referent) and read back **before** rendering. Previous attempt's `Fully synced` is not proof of next lesson readiness. If writing is off/unavailable/registration fails, allow useful continuation only as **explicitly unsaved** (never claim next lesson is `save-ready` or fabricate persisted IDs). Preserve privacy and do not silently retrofit Activities later.
7. **Response shape:** (i) concise past-lesson feedback and exactly one prior submission sync status, (ii) clearly delimited new lesson with communicative can-do, context, duration, working visual/context-based activities, learner preference task count, and one final Submit, (iii) vocabulary at end of new lesson. Never end solely with “Next: X,” a teaser, another command prompt, or a `Start lesson` button. Do not present another final-submit button except inside the next lesson itself.
8. **When no more graded lesson is appropriate:** Say which concrete stop condition applied and provide a complete optional self-study suggestion without claiming any auto-start. If technical limits prevent presenting a full usable form, show honest functional accessible fallback as allowed in the exercise rules. Do not make invented clickable controls.

## Specific acceptance examples

- Five-task Lost & Found submitted; three recognized/guided answers correct and independent pictured writing needs support. After exact write/readback, ASIT produces concise correction, **previous-attempt status**, and directly renders a new five-task lesson for the next skill from the active plan (e.g. past-event narrative), rather than a “Start next lesson” button. Spaced article review is scheduled/retained separately; do not endlessly drill locations.
- The same `ASIT_ATTEMPT_V2` is resent: do not write duplicate Attempts or register another next lesson; recover/re-render the existing next lesson if needed.
- Provider write succeeds for Attempts but projections fail: report `Attempt saved / Partial sync` and still deliver next lesson only with independently verified next preflight or explicit unsaved disclaimer.
- A learner says “stop for today, just mark the answers”: grade/save/report, no next form.
- Recording consent is `off`: grade and auto-continue **unsaved**, without Drive writes or fabricated sync badges.

## Efficiency guardrails

Only load this small reference on ASIT answer turns, not on general progress/capability questions. Use bounded learner state and no GitHub/repository reads. Do not manufacture audio, video, UI or evidence to satisfy variety rules. This contract does not claim background notifications or teacher actions between messages.
